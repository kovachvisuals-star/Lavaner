# LAVANER — підготовка релізу без кредитів Lovable

Цей документ стосується **лише** гілки `direct-seo-2026-10-18`. Продакшн `lavaner.ee` лишається на Lovable; автоматичного перенесення немає.

## Що вже є у GitHub
- Вихідний код ET/RU/EN, 78 URL, канонічні адреси та hreflang.
- Локальна Cloudflare Workers SSR-збірка з тестовим воркером `lavaner-staging`.
- Архів фотографій, відео, логотипа та іконок; автоматична перевірка відповідності media JSON.
- Read-only SEO-аудит усіх 78 адрес (окремо від тесту короткого списку).
- Безпечний вихід: стандартна форма запускає email, пряме надсилання через D1 і Turnstile залишається вимкненим до налаштування.
- Браузерні захисні заголовки і noindex для тестових `*.workers.dev` / `*.pages.dev`.

## Перед першою публікацією тестової версії
1. Створити/підключити власний Cloudflare акаунт. Не пересилати токени в ChatGPT і не записувати їх у GitHub код.
2. У GitHub → Repository settings → Secrets and variables → Actions: `CLOUDFLARE_ACCOUNT_ID`, `CLOUDFLARE_API_TOKEN` із мінімальними Workers дозволами.
3. У GitHub → Actions → **Deploy LAVANER to Cloudflare staging** запустити workflow з гілки `direct-seo-2026-10-18`.
4. Перевірити URL `lavaner-staging.*.workers.dev` вручну на телефоні та комп'ютері, без зміни DNS.
5. Звірити головну, усі сервіси, ET/RU/EN, фотографії, відео, мобільне меню, 404, HTTPS, sitemap/robots.
6. На staging має бути `X-Robots-Tag: noindex, nofollow`. На основному домені цього заголовка бути не повинно.

## Повноцінні заявки — окремий етап, НЕ увімкнено
Код уже містить backend `POST /api/quote`, міграцію `site/db/migrations/0001_quote_enquiries.sql` і Turnstile. Але цього **недостатньо** для використання у виробництві:
1. У Cloudflare створити D1 `lavaner-leads` та підставити реальний `database_id` з власного акаунта в `wrangler.jsonc` (приклад: `site/wrangler.d1.example.jsonc`).
2. Застосувати міграцію до віддаленої D1: з каталогу site `bunx wrangler d1 migrations apply lavaner-leads --remote`. Перед цим перевірити, що база саме та, яка створена для LAVANER.
3. Налаштувати Turnstile на домени staging і production, сайт-ключ — публічна build-time змінна `VITE_TURNSTILE_SITE_KEY`; **секрет** зберігати лише у Cloudflare Worker secret `TURNSTILE_SECRET`.
4. Переконатися, що робочі заявки доходять до відповідального менеджера (через захищений адмінінтерфейс, нотифікацію чи інтеграцію CRM). На даний момент лише збереження у D1 **не є** повідомленням менеджеру.
5. Узгодити політику зберігання персональних даних, право доступу та видалення, резервні копії і GDPR; перевірити rate limiting / WAF, а потім налаштувати `LEADS_ENABLED=true` у Cloudflare та `VITE_DIRECT_QUOTE_ENABLED=true` під час збірки. Без обох режимів та антиспам ключа прямі заявки не запускаються.
6. Протестувати одну контрольну заявку за згодою відповідальної особи, перевірити збереження і можливість прочитати її. Не пересилати телефони/email клієнтів у GitHub logs.

## Перехід домену — тільки після staging
- Перевірити контроль DNS та поточні записи; зробити резервну копію налаштувань.
- На staging перевірити усі URL, HTTP→HTTPS 301, www→apex, мови, метадані, реальні заявки, GA4.
- Оцінити SEO-ризик подвійної публікації та збереження поточних slug'ів.
- Лише після цього змінювати записи домену та тестувати SSL і Search Console.
- При невдачі повернути початкові DNS записи; оригінальний Lovable проєкт не видаляти.

## Відкриті завдання #1–#4: перевірка виконання
- #1: безпечний серверний прийом заявок ще не ввімкнено; mailto не дорівнює підтвердженому надсиланню. Залишається відкритим.
- #2: HTTP→HTTPS і SEO production необхідно перевірити після публікації, а не тільки за вихідним кодом. Залишається відкритим.
- #3: SEO-описи й локальну географію поліпшено в гілці, але не розгорнуто; контроль усіх мов і 78 URL ще потрібен. Залишається відкритим.
- #4: керування Google Business Profile не підтверджене; не вигадувати відгуки чи адресу. Залишається відкритим.
- Контактний serviceArea скориговано на Tallinn, Maardu, Viimsi ja Harjumaa; не заявляти охоплення всієї Естонії без підтвердження.
